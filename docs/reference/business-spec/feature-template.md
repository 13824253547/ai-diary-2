# 功能规格与测试用例模板

这是项目文档写法的模板，不是新增业务需求。简单功能可以合并字段成短段落；涉及隐私、状态转换和跨模块影响的功能应完整填写。

## 功能规格

```markdown
## MOD-000 功能名称

确认状态：初稿 / 已确认；适用版本：待定。
证据程度：交互已表达 / 展示已表达 / 预告未开放。

用户目标：谁在什么场景，要得到什么结果。
入口与前置：页面/上游流程、必须存在的数据或权限。
输入：字段、必填、格式、数量/长度、默认值；不明确项引用问题编号。

主流程：
1. 用户动作。
2. 系统产生可观察变化。
3. 结果及后续去向。

规则：去重、保存、关联数据、权限；通用规则以 BR 编号引用。
状态：操作前后状态，以及哪些内容可被修改。
异常与退出：空数据、无效目标、取消、返回、重复操作、失败/重试。
数据影响：新增/更新什么；哪些关联内容同步；留存规则。

- MOD-000-AC01：Given 前置条件，When 动作，Then 可判断的结果。
- MOD-000-AC02：Given 边界/异常，When 动作，Then 结果及数据状态。

依据：源文件/原型链接。
待确认：Q 编号。
变更记录：日期、修改原因、影响 AC 与用例。
```

验收标准要包含可观察结果。例如“支持选照片”无法判断通过；“只有2张有效照片时生成不可用，3张时可用”可以直接生成边界用例。不要给真实 AI 固定正文逐字匹配的验收条件，除非测试明确针对固定示例模式。

## 测试用例

| 字段 | 填写要求 |
| --- | --- |
| TC ID | 如 `TC-CRE-002-001`，稳定且唯一 |
| 关联需求/AC | 至少一个需求及具体验收 ID，必要时关联 BR |
| 用例名称 | 动作、条件和期望结果 |
| 层级 | 领域规则 / 组件 / 界面流程 / 真实服务集成 / 人工视觉验收 |
| 前置条件 | 数据、权限、已有状态、入口 |
| 测试数据 | 照片、日期、文本、公开范围等；与示例文案解耦 |
| 操作步骤 | 可重复执行的具体动作 |
| 预期结果 | 页面、数据、权限、关联对象的明确变化 |
| 执行记录 | 环境、版本、时间、执行人、通过/失败/阻塞/未执行 |
| 缺陷与证据 | 缺陷 ID、截图/日志/文件及复测结果 |

## 后续生成测试的指令模板

```text
根据 docs/reference/business-spec 中已确认的 MOD-000 功能规格、关联 BR、AC 和已关闭的 Q，生成测试用例。
每条用例提供 TC ID、需求/AC ID、层级、前置、数据、步骤、预期。
覆盖正常流程、数量/长度边界、空白/无效输入、取消/返回、重复操作、数据关联、隐私与权限。
遇到未定义规则，列出需要补充的问题，不编造预期结果。
把原型样例验证与真实服务集成验收分开；没有执行的用例标为未执行。
复用现有测试资产，指出新增覆盖范围，不用固定样例文字替代 AI 质量标准。
```

开发拆分也引用相同需求 ID：先确认业务结果与输入输出，再设计数据/API契约及任务。技术方案与产品规格分别维护，避免后端实现细节进入用户业务流程。
