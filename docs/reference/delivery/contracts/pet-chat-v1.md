# Pet Chat Contract v1

Version: `pet-chat-v1`

This first-party contract persists device-owned conversations and turns. Trusted replies are generated by a replaceable server-side provider from persisted conversation history; development replies remain explicitly marked `mock`. The API does not treat client-declared provider output as trusted.

## Identity and ordering

- Every operation requires `x-device-id`. Conversation reads and writes are scoped to the exact device identity. This header is an install identity/ownership key, not proof of a human account or cryptographic device authentication.
- The client supplies stable conversation, request, and message IDs. A request ID is unique within its device-owned conversation.
- User and assistant messages are stored separately and associated with a turn. A stable turn sequence determines display order, so out-of-order provider responses do not reorder the conversation.
- The welcome guide is not persisted as a user message.
- Text is trimmed at the boundary and whitespace-only turns are rejected. Q-003 still determines the final input length and keyboard policy.
- User-confirmed PET-001 scope is daily experiences, emotional companionship, travel memories, and diary expression. Server input policy rejects explicit out-of-scope generation (including code/scripts, fiction, and commercial copy), prompt override attempts, and recognized harmful operational requests with fixed `out_of_scope` / `unsafe_request` errors before writing the turn or calling the model.
- The Ark adapter also checks obvious code-shaped or harmful generated output before forwarding the offending SSE delta. Previously persisted completed messages that match the policy are excluded from future provider context. These deterministic patterns and the system prompt are defense-in-depth, not comprehensive semantic moderation; obfuscated/new abuse can bypass them.
- A device identity may have only one distinct active provider generation in this Nest process. Same-request idempotent subscribers share the active flight; another turn/retry is rejected as `chat_busy` before persistence while the device is busy. The client also blocks sends/retries while pending. The lock is process-local; multi-instance deployments need a shared lock, and caller-controlled `x-device-id` does not prevent identity rotation.

## API

- `GET /chat/conversations?page=1&pageSize=20` lists only conversations owned by the current device. `page` and `pageSize` are single decimal-integer query values; exponent, hexadecimal, fractional, whitespace-padded, and repeated values are rejected. Supported page sizes are 10, 20, 50, and 100.
- `GET /chat/conversations/:conversationId` reads the ordered messages and turn states for one owned conversation.
- `POST /chat/conversations/:conversationId/turns` persists one user message and a pending turn. Replaying the same request ID with the same user message is idempotent; changing the content under that request ID is rejected. Policy rejections return `out_of_scope` / `unsafe_request` without persistence or model invocation; a busy device receives `chat_busy`.
- `POST /chat/conversations/:conversationId/turns/:requestId/generate` generates the pending attempt on the server from the persisted conversation, then stores one `source: provider` assistant reply. The client submits only the attempt number; it cannot submit provider text or credentials. Duplicate generation requests within the same server process share the active operation, and completed-turn replay returns the stored result.
- `POST /chat/conversations/:conversationId/turns/:requestId/generate/stream` uses the same device, conversation, and attempt checks, and streams server-generated text as Server-Sent Events. `event: delta` carries `{"text":"..."}` fragments for immediate display; `event: complete` carries the versioned conversation envelope only after the full reply is persisted; `event: error` carries a fixed error `code`. Identity/input errors raised before streaming retain the normal HTTP error envelope. Repeated in-process requests share generation; a later subscriber receives the terminal event without replaying earlier deltas.
- `POST /chat/conversations/:conversationId/turns/:requestId/reply` stores a reply only for the current pending attempt. Replaying the same result does not create a duplicate assistant message; a different result cannot replace an already completed response.
- `POST /chat/conversations/:conversationId/turns/:requestId/failure` stores only the fixed failure code (`timeout`, `cancelled`, `provider_failed`), never the provider's raw error text.
- `POST /chat/conversations/:conversationId/turns/:requestId/retry` advances a failed request to the explicitly supplied next attempt. Replaying the same pending attempt is idempotent. The contract does not choose an automatic retry count or timing.
- Production turn creation and retry fail closed unless `PET_CHAT_PROVIDER=ark-openai-compatible` and the server-only `PET_CHAT_BASE_URL`, `PET_CHAT_MODEL`, and `PET_CHAT_API_KEY` are configured. When configured, only the server-side `generate` operation may persist provider replies; production rejects client-submitted mock or provider replies. Development may persist explicitly marked `source: mock` replies, and every non-test runtime rejects client-declared `source: provider`.
- The initial Ark-compatible adapter uses `PET_CHAT_TIMEOUT_MS`, `PET_CHAT_TEMPERATURE`, `PET_CHAT_MAX_TOKENS`, and `PET_CHAT_HISTORY_ITEMS`; these are provider engineering settings, not confirmation of Q-002 quality, cancellation, or retry policy. Chat settings are isolated from the shared `AI_PROVIDER_*` diary generation/rewrite settings.

## Persistence and open decisions

The Prisma schema and migration define device-owned conversations, turns, and ordered messages. The additive migration was deployed to the local `ai_diary` database during the authorized DEV-13 work and verified with migration status/schema diff; this does not establish a production deployment or user-facing retention promise.

The controller validates query wire values after device identity and the service repeats pagination object/type/range validation before database access.

The client now calls `GET /chat/conversations?page=1&pageSize=10`, followed by a device-scoped detail GET for the first non-empty item on that page, when the pet page opens without an explicit conversation ID. Explicit anchor-linked IDs take precedence. A failed read does not mean an empty history or permit a new send; the existing input action retries the read. Only successfully persisted turns can be restored.

Q-001 still determines retention duration, deletion/cleanup, and cross-device recovery. No TTL, cross-device transfer, or deletion policy is inferred here. The same-device reopen behavior does not establish a permanent user-facing retention promise.

Q-002 remains open for model quality, comprehensive moderation, timeout/cancellation/retry policy, and other AI modules. The user-confirmed PET-001 boundary is implemented with deterministic checks and system instructions; it is not a guarantee against semantic evasion. Q-003 still determines the final message length and supported keyboard matrix. The API stores source (`mock`/`provider`) explicitly and never silently turns persistence/provider failure into a successful mock turn. The local `backend/.env` has an isolated Ark configuration and a provider smoke test was recorded in DEV-13; production credentials and provider quality remain unverified.
