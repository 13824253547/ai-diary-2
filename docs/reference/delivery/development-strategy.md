# 开发优先的迭代策略

日期：2026-10-16。依据：用户批准“开发轮 → 集中测试轮 → 问题返工轮 → 复测轮”，并新增依赖优先的易到难排序及每项最多两轮缺陷返工。此策略替代旧提示词的逐任务测试收口节奏，不改变 FSD、验收条件、已确认业务规则和正式 UI/UX 边界。

阶段顺序：后续以 `DEV-N → TEST-N → DEV-(N+1) → TEST-(N+1)` 迭代，直到原始范围全部真实验收通过。阶段状态及仍待验证范围记录在 [开发台账](reports/development-progress.md) 和 [当前执行快照](reports/current-execution-snapshot.md)。

## 开发轮

- 先检查 git status，保留用户所有未提交修改、删除与新增文件。只以当前仓库为事实来源。
- 开始新轮时读项目规则、README、execution-context、decision-register、coverage、策略、外部依赖清单及台账；连续推进同一轮只核对变动文件和当前任务，不反复全文重读不变基线。
- 读对应 task、CASE、契约、源码和配置，将验收作为开发目标，不把“没有测试证据”当作“不能开发”。
- 每轮按 task 明确依赖建立可执行队列，并给任务标记复杂度 `S / M / L`：`S` 为局部、少层次、无 schema/外部集成的改动；`M` 为多层接线或有明确状态/并发边界的改动；`L` 为跨域持久化、安全/隐私、平台/供应商或高不确定性工作。该标记只用于安排先后，不改变业务重要性或验收标准。
- 严格依赖优先：先完成当前可执行任务所需的前置能力；在依赖均满足的候选任务中按 `S → M → L` 推进，完成较易候选后再进入较难项。不要为了“容易”越过实际依赖，也不要让一个被决策/环境阻塞的分支挡住无依赖的候选任务。当前优先队列及复杂度依据写入开发台账；跳过的任务仍保留原始范围和未完成状态。
- 优先完成自有能力，再完成外部依赖任务的本地业务部分。框架/库、系统权限、自有后端和待产品决策必须分开分类。
- 外部服务缺凭据/供应商时，开发接口契约、请求/会话 ID、输入版本、状态机、权限、持久化、取消/幂等/并发/错误处理，并用同接口 mock 驱动开发；真实外部调用和质量评测延期。
- mock 集中在服务/adapter/provider 边界，不把固定结果写进正式页面；显式区分 mock 与真实来源，禁止真实适配器失败时静默切换为 mock 成功，禁止把模拟结果记为真实渠道交付或真实 AI 产物。
- 开发 mock 可以拥有当前开发模式下的独立记录；不得混入真实用户数据、跨设备身份或正式交付成功记录。保持既有 mock 能力，不擅自替换已接通的真实保存/查询服务。
- 本轮 mock 授权不等于自部署模型、下载大模型、付费调用、上传用户数据或改变包体积预算的授权。
- 日记正文排版、图片处理、PDF、相册、系统分享等可用框架/库开发的部分继续推进；系统权限或设备不可用仅阻塞设备验证，不阻塞可明确实现的代码。
- 产品规则缺失只暂停受影响分支，登记最小待决策事项；不将建议默认值冒充确认，不擅自改变 UI/UX、路由、按钮状态、提示或用户路径。需要可见行为改动时列出具体授权边界。
- 开发阶段不以每项完成立即新增/复跑测试为强制门槛，不重复执行全量 Jest/e2e、模拟器 CASE、截图或 provider 评测。允许在必要时做类型/编译/静态差异检查，或针对会影响数据安全的最小验证；如实记录“未测试”。
- 不删除现有测试或修改断言以适应不正确实现。中断时未验证的测试代码保持“已编写、未验证”，不得沿用旧报告宣称通过。
- CRE-002 在轮次启动或相关代码变化时核对源码与既有证据；无相关变化时不必每次跑 14 项回归或重试原生权限异常。iOS blocker 保留至 TEST 轮补真实证据。

## 阶段切换

DEV 轮转入 TEST 轮前，必须对全部 42 项任务形成开发结论：本轮实现完成待测试、mock 业务完成待外部接入、已有实现待复验、真实适配器延期，或具体产品/权限/UI 授权阻塞。未盘点和实施中不能被计作已开发完成。

每项记录源码路径、业务缺口、mock 范围、真实接入缺口及待测 CASE。有独立可开发工作时继续 DEV；仅有外部/决策阻塞时交接清单并进入可执行的集中 TEST，不等待第三方把整轮拖住。外部延期不等于原任务完成。

## 测试轮与返工

TEST 轮基于当前实现统一执行单元、领域、契约、隔离集成、设备、文件及端到端 CASE。mock 测试只证明状态与编排；真实 provider 输出质量、实际设备文件和渠道交付仍单独验收。

每项任务的验收返工上限为：初次开发不计返工；初次集中验收失败后，最多允许两轮集中缺陷修复，每轮修复后进行对应复测。两轮修复后仍未通过，标记为“达到返工上限，暂跳”，保留失败 CASE、缺陷与证据，暂停该任务当前缺陷线并继续其他依赖就绪的任务。暂跳不代表通过、关闭或从全局范围移除；只有新证据、依赖变化或用户指示后才恢复。

每项 task 在开发台账保留初次开发轮次、已用修复轮数 `0/2`、对应 TEST 轮/复测结论、当前缺陷及暂跳/恢复条件。一次修复轮是针对同一轮集中测试已记录问题的一次合并修复批次；测试命令无代码/断言变更的重跑不是修复轮，但不得反复运行未变化且已知必然失败的检查。不得通过删除、弱化断言或改变验收标准来规避上限。

因设备权限、凭据、外部服务或待确认产品规则无法执行的情况，登记为环境/决策阻塞并暂跳受影响分支；没有实际修复机会时不消耗缺陷返工次数。发现数据损坏、越权或隐私泄漏等高严重度问题时，立即停止相关测试与危险操作并优先处理；未消除前不能以返工上限为由恢复危险流程，也不能声称验收通过。

发现问题先记录 CASE、输入、环境、预期、实际、证据、严重度和影响；按以上上限集中形成 DEV 修复清单，避免每遇一个失败就切回零散补开发。

全部 reset/清表/迁移测试须使用明确隔离的临时资源，未经授权不得影响开发库、生产或真实用户数据。服务凭据不打印；真实付费/供应商调用须另获授权。

## 记录与统计

开发状态与验收状态是两个维度：开发轮更新 task 当前实现段及开发台账；CASE、验收矩阵仅在取得实际证据后改变结果。台账同时记录依赖、复杂度、修复轮计数和暂跳原因；四份原台账保留并记录阶段/变化，不反复改写历史证据或给未运行 CASE 标通过。

开发台账统计本轮实现完成、mock 业务完成、延期、实施中、未盘点的任务数；不与 225 条验收混算，不凭测试数量推导开发百分比。待完整源码盘点前不报告开发完成百分比。

验收进度继续按 coverage 的有效总数与矩阵 passed 项计算。允许 DEV 轮中验收进度不变化，汇报应优先说明实际开发增量。只有所有原始要求真实通过，才可将全局 goal 标为完成。
