## 任务内容

- 将关键词即时回复替换为真实陪伴生成能力和会话仓库。发送用户消息、请求回复、保存会话与重开加载均读取同一用户的真实记录；欢迎语可以是产品引导，不能代替已发送消息。
- 定义消息 ID、角色、顺序、请求状态与请求标识在 UI 和服务之间的映射。发送中、失败及重试在页面给出可观察状态；重复点击、响应丢失和乱序回复不得生成重复消息或把旧回复接在错误会话之后。
- 保留空白拦截、去空白、角色气泡、滚动定位及可用平台的键盘行为。输入长度和 AI 质量、时限等按 Q-002/Q-003 决策；用户已局部确认聊天业务范围和安全拦截规则，不沿用 mock 关键词为产品规则。
- 对本机退出 / 重开及身份切换验证会话归属和留存；真实集成以隔离账号和真实服务响应为证据。

## DEV-20 PET-001 失败 turn 重试后的原始顺序

- 根因：某条消息首次 `beginTurn` 因网络/服务失败时只保留在 Store；用户之后发送的新 turn 成功进入服务端，Store 用服务端快照重建消息时把所有 local-only request 统一追加至末尾。重试旧消息并使其落库后，服务端新分配的 sequence 也晚于后续消息，视觉上旧失败气泡/回复因此掉到后面。
- 修复：合并会话快照时以当前 Store 中已建立的请求先后作为稳定顺序，按 request ID 分组重建每个 turn 的 user/assistant/status 消息；新发现的服务端 turns 接在已有顺序之后。旧 local-only turn 后续成功持久化时保留原 UI 位置，正常服务端历史仍按 turn sequence 构建。
- 回归：模拟旧 turn 首轮 begin 失败 → 新 turn 持久化并完成 → 重试旧 turn 并完成，验证用户/助手消息始终按初始发送顺序排列且不重复。前端 chat 3 suites / 21 tests、root typecheck、`git diff --check` 通过。该排序基于当前 Store 生命周期内保留的请求顺序；若 App 在 local-only turn 尚未落库时退出，该轮是否恢复仍受 Q-001 留存/恢复规则约束。

## DEV-27 Provider 单次请求时限（2026-10-22）

- Ark 宠物聊天 Provider 默认超时为 `240000` ms；环境变量可设更短时限，超过 4 分钟的配置封顶。计时在后端请求体准备完成、即将提交模型请求时启动。每次新的 Provider attempt 独立计时，不把前一次失败等待累计到下一次。
